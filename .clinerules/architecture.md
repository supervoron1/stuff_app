# Архитектура проекта «Запасы»

> Схематичное описание слоёв, чтобы агент не нарушал границы. Дополни своими требованиями.

## Слои и их границы

- `app/api/` — REST-роуты для синхронизации/аудита/загрузки фото.
- `app/page.tsx`, `components/` — UI (клиентские и серверные компоненты).
- `hooks/` — клиентская логика состояния и данных (`use-inventory`, `use-user`).
- `lib/` — серверный и общий код: `prisma.ts`, `supabase.ts`, `data.ts`, `actions.ts`, `sync.ts`, `db.ts`, `types.ts`, `constants.ts`.
- `prisma/` — схема БД и миграции.

## Ключевые принципы

- **Offline-first**: источник истины для UI — локальный кэш Dexie (`lib/db.ts`); сервер — база PostgreSQL через Prisma.
- **Outbox-паттерн**: изменения офлайн кладутся в очередь (`outbox`) и отправляются при появлении сети через `lib/sync.ts`.
- **Last-write-wins**: конфликты разрешаются по `updatedAt` — при изменениях всегда обновлять `updatedAt`.
- **Аудит**: каждая мутация пишет `AuditLog` (`action`, `entity`, `entityId`, `userName`, значения до/после).
- **Сервер — источник правды** для БД: клиент не ходит в Prisma напрямую.
- Типы между слоями согласуются через `lib/types.ts`.

## Что согласовывать до реализации

- Изменения схемы Prisma → миграция + обновление типов во всех слоях.
- Изменение формата синхронизации → совместимость со старыми кэшами (Dexie).
- Новые API-эндпоинты → безопасность (валидация через zod, авторизация при необходимости).
