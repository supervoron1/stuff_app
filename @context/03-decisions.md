# Ключевые решения (Decision Log)

Здесь собраны решения, принятые при разработке, и их обоснование. Это позволит не повторять анализ при новых вопросах.

## D1. Стек: Next.js 16 + React 19 + TypeScript + Tailwind 4
**Решение:** Next.js 16 (App Router), React 19, TypeScript (strict), Tailwind CSS 4.
**Почему:** единая платформа (UI + API + деплой на Vercel), современный App Router, Server Actions для мутаций, мобильный UI на Tailwind.

## D2. Офлайн-синхронизация: outbox pattern на Dexie (IndexedDB)
**Решение:** локальный кэш `categories`/`products` + очередь `outbox` в IndexedDB (Dexie); при появлении сети — push очереди на сервер, затем полный снимок (pull).
**Почему:** нужна работа без интернета; outbox гарантирует, что офлайн-изменения не потеряются и будут отправлены при первой возможности.
**Детали:** ID генерируются на клиенте (uuid) — без этого нельзя создавать записи офлайн и потом синхронизировать.

## D3. Конфликты: last-write-wins по `updatedAt`
**Решение:** при одновременном изменении с двух устройств побеждает запись с более поздним `updatedAt` (товар) / `createdAt` (операция очереди).
**Почему:** просто и предсказуемо для небольшого объёма данных (≤200 товаров), согласовано с пользователем.

## D4. База данных: Neon (PostgreSQL) вместо Supabase
**Проблема:** Supabase на бесплатном тарифе — direct-подключение к БД **только по IPv6** (порт 5432 недоступен с IPv4-сети пользователя); connection pooler для проекта не был включён → ошибка `P1001` / `tenant not found`.
**Решение:** основная БД — **Neon** (бесплатный PostgreSQL, работает по IPv4, совместим с Prisma и Vercel). Supabase оставлен **только для фото** (его API доступен по IPv4).
**Почему:** минимальные правки кода (только `DATABASE_URL`), мгновенная работоспособность из локальной сети и на Vercel.

## D5. Фото: Supabase Storage (bucket `products`, public)
**Решение:** загрузка фото через `POST /api/upload` → Supabase Storage; bucket создаётся автоматически при первой загрузке.
**Почему:** не хочется хранить файлы в БД; Supabase Storage бесплатен и уже используется в проекте.
**Ограничение:** загрузка/замена фото — **только онлайн** (офлайн-загрузку не реализуем — файлы всё равно нужно передать на сервер).

## D6. Аудит: простое логирование с именем пользователя
**Решение:** таблица `AuditLog (action, entity, entityId, oldValue, newValue, userName, createdAt)`; имя пользователя запрашивается в UI и хранится в localStorage.
**Почему:** по ТЗ нужна авторизация без пароля — только фиксация «кто и что менял».

## D7. Оптимизация производительности на Vercel (важная находка)
**Проблема:** тап по индикатору занимал несколько секунд на Vercel (локально мгновенно).
**Причина:** до **3 последовательных сетевых запросов** к Serverless-функции `/api/sync` (POST push → GET pull → GET в `syncNow`) + **«холодный старт»** Lambda-контейнера на бесплатном тарифе; кнопка блокировалась через `await`.
**Решение:**
1. `cycleStatus` → **оптимистичный отклик**: запись в IndexedDB + мгновенное обновление UI; синхронизация в фоне (без блокировки).
2. `POST /api/sync` → применяет операции **и возвращает свежий снимок** в том же ответе (1 запрос вместо 3).
3. `syncNow` при пустой очереди делает 1 GET.
**Рекомендация пользователю:** ставить функции в регион, близкий к БД; при желании — настроить Incognito-миграцию хостинга.

## D8. PWA: манифест + Service Worker
**Решение:** `app/manifest.ts` + `public/sw.js` (кэш app shell, network-first для API) + иконки (`scripts/generate-icons.mjs`).
**Почему:** установка на главный экран, офлайн-открытие, полноэкранный режим.

## D11. Фильтрация по статусу: скрытие категорий без подходящих товаров
**Решение:** при выбранном фильтре по статусу (🟢 Есть / 🟡 Мало / 🔴 Нет) в `components/inventory.tsx` отображаются **только категории, где есть хотя бы один товар с этим статусом** (`visibleCategories`); товары фильтруются по статусу и поиску (`productsByCategory`). Если ни одна категория не подошла — глобальное пустое состояние «Нет товаров с таким статусом». При создании нового товара фильтр сбрасывается на «Все».
**Почему:** по требованию пользователя — при выборе состояния нужно видеть только релевантные категории и товары; пустые карточки «Нет товаров с таким статусом» мешали.
**Детали / граничные случаи:**
- Режим «Все»: пустые категории остаются видимыми («Нет товаров») — иначе в них нельзя добавить первый товар.
- Поиск + статус: категория скрывается, если её товары не совпадают с поиском даже при совпадающем статусе (консистентно).
- Создание товара при активном фильтре: новый товар получает `SUFFICIENT` по умолчанию и был бы невидим → фильтр автоматически сбрасывается на «Все» при открытии формы.
- Смена статуса последнего видимого товара в категории → категория исчезает (ожидаемо); глобальное пустое состояние объясняет отсутствие совпадений.
- Офлайн: фильтрация полностью клиентская (IndexedDB), работает без сети.

## D12. Единые подписи статусов для UI и аудита
**Проблема:** в истории изменений (аудит) статусы записывались как «Достаточно»/«Мало»/«Отсутствует», а в UI — «Есть»/«Мало»/«Нет» — историю было читать несогласованно.
**Решение:** единый источник `STATUS_LABELS` в `lib/constants.ts` («Есть»/«Мало»/«Нет») используется и в UI, и при записи аудита (`lib/actions.ts`, `app/api/sync/route.ts`); локальная копия подписей из `app/api/sync/route.ts` удалена.
**Почему:** одна точка правды для подписей; история читается в тех же терминах, что и интерфейс.
**Примечание:** уже записанные в БД записи аудита со старыми подписями («Достаточно»/«Отсутствует») остаются историческими данными и не переписываются.

## D13. Аккордеон категорий + «Свернуть все/Развернуть все»
**Проблема:** при большом количестве категорий список растягивался — нужен компактный просмотр.
**Решение:** категории по умолчанию развёрнуты; тап по заголовку сворачивает/разворачивает (шеврон ▾/▸, счётчик видимых товаров, `aria-expanded`). Кнопка «Свернуть все/Развернуть все» (справа над списком) действует только на видимые категории. При активном фильтре статуса или непустом поиске категории **принудительно развёрнуты** (`forceExpand`), кнопка «Свернуть все» при этом отключена — иначе отфильтрованные товары оказались бы спрятаны.
**Почему:** фильтр/поиск имеют смысл только когда товары видны; сворачивание нужно для компактного просмотра в режиме «Все».
**Детали:** состояние `collapsedIds` (Set id) в `useState` — не сбрасывается при синхронизации (компонент не ремоунтится); новая категория развёрнута; кнопка «+» разворачивает свою категорию. Свёрнутость, заданная пользователем, сохраняется «под» фильтром и возвращается после его сброса.

## D14. Индикатор наличия: цветная галочка ✓ (вместо «пилюли» и кружка)
**Решение:** по доработке дизайнера индикатор статуса в строке товара — **просто цветная галочка ✓** без фона: цвет зависит от статуса (зелёный/жёлтый/красный). Промежуточная версия с галочкой в цветном кружке отвергнута. Компонент `components/stock-check.tsx` (SVG-галочка, цвет из `STATUS_COLORS`, тап циклично меняет статус, `aria-label` для доступности; интерактивная тап-зона 40×40 прозрачная). Старый `components/stock-indicator.tsx` **оставлен в репозитории, но не используется** (по просьбе дизайнера не удалять).
**Почему:** новый визуальный стиль по ТЗ дизайнера; компактнее в строке товара.
**Примечание:** текстовая подпись статуса из строки товара убрана — статус читается по цвету кружка; подписи по-прежнему видны в фильтрах. Текст легко вернуть при необходимости (неинтерактивный режим компонента).
## D15. Перетаскивание товаров внутри категории (drag-n-drop)
**Решение:** порядок товаров в категории задаётся вручную перетаскиванием за ручку ⠿; для реализации добавлено поле `Product.sortOrder`, новая операция outbox `reorderProducts` и библиотека `@dnd-kit` (`core` + `sortable` + `utilities`).
**Почему:** по требованию пользователя — внутри категорий нужно менять местами товары с сохранением порядка.
**Детали / граничные случаи:**
- Перетаскивание доступно только в режиме «Все» и без поиска (в отфильтрованном списке позиция неоднозначна); скрыто при <2 товарах в категории.
- Только внутри одной категории (перенос между категориями не реализован).
- Операция `reorderProducts` несёт полный упорядоченный список id товаров категории и целиком заменяет `sortOrder` (last-write-wins на уровне категории).
- Новый товар создаётся в конец категории (`sortOrder = max+1`); при создании офлайн значение передаётся в payload `createProduct`.
- Существующие товары получили `sortOrder` по текущему алфавитному порядку (бэкофилл в миграции `20260811190635_product_sort_order`).
- Перестановки не пишутся в аудит (по соглашению с пользователем).
- Drag-зона: ручка ⠿ + название товара (левая часть строки, включая фото/описание). Сенсоры: MouseSensor (distance 6) — мышь, TouchSensor (delay 200 мс, tolerance 8) — тач через long-press, чтобы не блокировать прокрутку списка. Клики по галочке статуса и кнопкам ✎/✕ не перехватываются.

## D16. Устранение задержки перетаскивания товаров (оптимистичный UI)
**Проблема:** после перетаскивания товар «возвращался» на прежнее место и вставал куда нужно только после сетевой синхронизации (2-3 сек), индикатор «Ожидает: N» мигал.
**Причины:**
1. `SortableContext` не обновлялся синхронно в `onDragEnd` — dnd-kit анимировал возврат элемента на исходную позицию.
2. Гонка: `refresh()` запускался параллельно с локальной записью — `replaceCache` мог перезаписать свежие `sortOrder` старым снимком, и порядок применялся только следующим push.
3. Позиция менялась только после полного сетевого цикла (`POST /api/sync` + snapshot).
**Решение:**
- `optimisticReorder` в `use-inventory.ts` — синхронно обновляет порядок в state при `onDragEnd` (мгновенный UI без ожидания сети/БД); dnd-kit оставляет элемент на новом месте.
- `handleDragEnd` переписан последовательно: `optimisticReorder` → `await reorderProductsLocal` → `await refreshLocal` → фоновая отправка с debounce 400 мс (`scheduleSync`).
- `doSync`: повторный проход, если во время синхронизации в outbox добавились операции; `pendingSyncRef` — ещё один проход сразу после занятой синхронизации.
- При ошибке локальной записи — откат порядка из кэша и сообщение.

## D17. Быстрые тапы по галочке статуса (оптимистичный цикл)
**Проблема:** при 2-3 быстрых тапах по одному товару статус «застревал» на первом выбранном значении, появлялось «Ожидает: N», и 1-2 сек тапы «не воспринимались».
**Причины:**
1. Следующий статус считался от `product.stockStatus` из замыкания текущего рендера — при быстрых тапах рендер не успевал обновиться, все тапы ставили один и тот же статус.
2. Каждый тап создавал операцию в outbox и вызывал сетевую синхронизацию (1-2 сек) — «Ожидает: N» висел до завершения POST.
**Решение:**
- `pendingStatusRef` (Map id → статус) — следующий статус считается от последнего «запушенного» тапом, а не от устаревшего рендера; цикл работает корректно даже при 3 тапах подряд.
- `optimisticSetStatus` в `use-inventory.ts` — синхронное обновление status в state (мгновенный UI без ожидания сети/БД).
- Отложенная запись (debounce 300 мс): в IndexedDB/outbox попадает только финальный статус после серии тапов.
- Коалесинг в `setStockStatusLocal`: из outbox удаляются предыдущие операции смены статуса того же товара.
- `scheduleSync` (debounce 400 мс) — одна фоновая синхронизация на серию тапов.

## D18. Поиск: скрытие категорий без совпадений
**Проблема:** при вводе строки поиска категории без совпадающих товаров (и пустые) оставались видимыми, что мешало ориентироваться.
**Решение:** `visibleCategories` теперь фильтрует категории по наличию товаров, прошедших и фильтр статуса, и строку поиска (по аналогии с фильтрами, D11):
- «Все» и без поиска — показываются все категории (включая пустые, чтобы можно было добавить первый товар).
- Непустой поиск и/или фильтр статуса — только категории, где есть хотя бы один подходящий товар.
- При отсутствии результатов показывается «Ничего не найдено по запросу "..."» (аналог «Нет товаров с таким статусом»).
- Поиск, как и раньше, идёт по названию товара.

## D19. Обновление PWA «как в Play Market» (версионность + баннер)
**Решение:** механизм обновления установленного PWA с уведомлением пользователя (вариант А):
- `public/sw.js`: версия кэша в имени (`CACHE_NAME = "inventory-vN"`); `skipWaiting()` убран из `install` — активация новой версии только по решению пользователя (сообщение `SKIP_WAITING`); на `activate` по-прежнему удаляются старые кэши и вызывается `clients.claim()`.
- `components/pwa-register.tsx`: регистрация с `updateViaCache: "none"`; периодическая проверка `registration.update()` каждые 60 сек + на `focus`/`visibilitychange`; при появлении новой версии (`updatefound` → `installed` + есть контролирующий SW) показывается баннер «Доступна новая версия» с кнопками «Обновить»/«Позже»; по «Обновить» — `postMessage({type: "SKIP_WAITING"})`, по `controllerchange` — `location.reload()`.
- `app/manifest.ts`: добавлен стабильный `id` (важно для распознавания PWA). Поле `version` не добавлено — тип `MetadataRoute.Manifest` в Next 16 его не поддерживает; версия приложения выражается версией кэша в `sw.js`.
**Ограничения:** обновление происходит только при открытом приложении (как у всех PWA); на iOS Safari `registration.update()` в standalone-PWA может игнорироваться — там надёжная проверка при запуске/навигации.

## D20. Тёмная и светлая тема
**Решение:** class-based dark mode в Tailwind 4 (`@custom-variant dark`) + хук `useTheme` (light/dark/system), выбор хранится в localStorage (локально на устройстве).
**Детали:**
- По умолчанию — светлая до первого ручного переключения; переключатель в шапке (☀️ → 🌙 → 🖥 система) рядом с «Историей» и «Обновить».
- Анти-flash: инлайн-скрипт в `<head>` (`layout.tsx`) ставит класс `dark` до первого рендера, если сохранено dark или system+тёмная система.
- `globals.css`: `@custom-variant dark`; цвета статусов через CSS-переменные (`--status-sufficient/low/out`) с осветлением в `.dark`; `stock-check.tsx` использует `var(--status-*)`.
- Акцентные кнопки в тёмной теме — `dark:bg-green-500` (вместо green-600); фильтры — инвертированные пилюли (активный `dark:bg-white dark:text-gray-900`).
- PWA: `meta theme-color` обновляется динамически (`#ffffff`/`#0a0a0a`); манифест статичен (ограничение установленного PWA).

## D22. Исправление hydration mismatch
**Проблема:** в консоли ошибка «A tree hydrated but some attributes of the server rendered HTML didn't match the client properties» + значок Next — 1 Issue.
**Причины:**
1. Анти-flash скрипт тёмной темы добавляет класс `dark` на `<html>` до гидратации React — у серверного HTML и клиента расходятся атрибуты `class`.
2. `useInventory` инициализировал `online` от `navigator.onLine` на клиенте, а на сервере — `true`: при несовпадении состояния сети расходился текст «в сети/офлайн».
**Решение:**
- `suppressHydrationWarning` на `<html>` в `app/layout.tsx` (стандартный паттерн для class-based theme).
- `use-inventory.ts`: `online` инициализируется `true` (hydration-safe), реальное `navigator.onLine` уточняется в `useEffect` сразу после гидратации.
